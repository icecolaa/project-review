① 使用说明与原则How to Use

本文档把 2026 年 8–10 月的项目沉淀整理为面试可用的素材：四条技术叙事线给出整体故事，项目话术给出每个项目的 30 秒版本与深挖点，面试题库给出高频问题与结合项目的参考答案。

三条使用原则：
  1. 诚实为上：所有答案都来自真实代码。模拟的就说模拟（妙记 Lite 的转写是规则模拟），进行中的就说进行中（ai-project 的 RAG 链路）——被追问实现细节时，真实经历才经得起三层追问。
  2. 数字优先：每个故事带具体数字（225 次提交、28 套测试、20 万手交叉验证），比形容词可信。
  3. 取舍叙事：面试官最想听的不是「我用了什么」，而是「我为什么这么选、放弃了什么」（如 GoTrip 放弃实时协作）。

③ 四条技术叙事线Story Lines

叙事线一：AI 应用工程化（GoTrip 为载体）

「我不只会调大模型 API，而是解决 AI 落地的四个工程问题：输出不可控（JSON 模式 + Schema 转换 + 防幻觉过滤）、服务不可用（规则引擎离线兜底 + 双源降级）、响应太慢（异步 job 化 + 流式）、合规风险（小程序 AI 类目驳回后的去 AI 化改造）。」

叙事线二：RAG 与记忆体系（spring-ai 为载体）

「从零搭过完整 RAG 链路：文档读取→三种拆分器选型→向量化（适配批次上限）→Milvus→查询重写→重排序（top200 粗筛→rerank 精排）；对话记忆从内存演进到 Redis/MySQL，再加摘要遗忘和 PII 脱敏 Advisor。」

叙事线三：多 Agent 协作系统（work-together 为载体）

「把多 AI 协作本身做成了可发布的产品：主持方负责 Spec/Plan/Verify，执行方按文件归属并行干活；调度器是状态机，验收靠指纹比对，执行必须留下可见性证据——解决的是 Agent 干活『看不见、验不了、会越界』三个问题。」

叙事线四：博弈 AI 与正确性验证（party-games 为载体）

「LLM 之外的另一条 AI 线：五子棋的搜索算法（棋型评估+迭代加深 α-β+强制应手）、德州的蒙特卡洛胜率+对手建模、掼蛋的启发式拆牌代价。更重要的是验证方法论：20 万手交叉验证、AA 胜率校准到 85.2%、25 万局 fuzz + 与参考引擎差分测试。」

④ GoTrip —— 旗舰项目话术Pitch

30 秒电梯版

「我独立完成了一个协作旅行规划平台，React + TypeScript 的 Web 端加微信原生小程序双端，25 天 225 次提交，约两万行前端、九千行小程序代码。核心特色是 AI 应用工程化：用户粘贴小红书攻略文本，大模型解析成结构化行程落库，还能按天号精准重写某几天；所有 AI 功能都有规则引擎兜底，AI 挂了功能不挂。项目完整经历了『自托管全栈 → 微信云托管 → CloudBase BaaS』的架构演进，包括一次主动的架构反转，以及小程序 AI 深度合成类目被驳回后的合规改造，最后用 190 张截图的自动化验收全绿发布。」

STAR 展开

S 情境
国内没有好用的协作旅行规划工具，国外产品（TREK）不支持高德地图和微信生态。
T 任务
独立完成产品从 0 到 1 并上架微信小程序，覆盖行程编排、地图、AA 记账、AI 解析攻略。
A 行动
Monorepo（client/server/shared/miniprogram-app 四包）；高德瓦片接入 Leaflet 并自实现 WGS-84→GCJ-02 坐标转换；AI 链路做 JSON 模式+防幻觉过滤+离线兜底；微信 callContainer 15 秒硬超时倒逼出异步 job 化；发现 CloudBase 行级权限做不到跨用户共享后，主动砍掉自建 WebSocket 实时协作，换取最短合规发布路径。
R 结果
小程序 1.5.20 发布，七轮清单验收 46/46 全绿；沉淀 65 条目交接日志和 7 条红线规则手册；性能优化把首屏云调用从约 100 次降到 36 次。

预判追问与深挖点

  • 为什么反转架构？（权限模型 + 合规 + 运维成本；冲突面被「单人单库」直接消掉）
  • AI 解析怎么保证质量？（response_format json_object、保留原文顺序、不编造价格、extractJson 兼容围栏、失败走正则兜底）
  • 讲一次生产事故？（缓存键漏 passengers 导致 9 人查询污染 2 人；公网挂 3 天的全库导出接口复盘）
  • 地图坐标系？（GPS 是 WGS-84，高德瓦片是 GCJ-02，不转换会偏移几百米，实现含克拉索夫斯基椭球参数和境内外判断）

⑤ 聚会游戏合集 —— 话术Pitch

30 秒电梯版

「一个 9 款游戏的联机聚会合集，纯 Node 零依赖，一个 140 行的注册表式入口挂载全部游戏。AI 是重点：五子棋是迭代加深 α-β 剪枝加棋型评估，象棋有 Zobrist 置换表和静态搜索，德州扑克是蒙特卡洛胜率加对手建模。我更想强调正确性验证：牌力评估器和独立暴力实现交叉验证 20 万手随机牌完全一致，AA 单挑胜率蒙特卡洛校准到 85.2%（公认值 85% 左右），掼蛋 fuzz 25 万局、和参考引擎差分对跑修出 4 类真实缺陷。整个仓库 28 套测试、2600 多断言。」

深挖点

  • 注册表式架构：新增游戏 = 一条注册项；三种通信并存（长轮询/WS/HTTP API）
  • 外部引擎宿主 engine-host：懒启动、单飞队列、超时看门狗，以及修复的三个真实并发 bug（每个都能展开讲竞态窗口）
  • 许可工程：MIT 自研与 GPL vendor（xqwlight 13,673 行）用 Web Worker 边界隔离，不混合
  • 差分测试方法论：AI 出牌合法率变成可度量指标（missing=0）

⑥ 多 AI 协作系统 —— 话术Pitch

30 秒电梯版

「work-together 是我做的多 AI 桌面协作工作流，已上架 SkillHub（v1.2.0，五维评测 4.6/5）。思路是把 AI 当团队用：一个主持 AI 写 Spec 和 Plan、做验收，把执行包派给另外两个 AI 桌面会话并行执行。三个关键设计：一是文件归属做并发控制，任务包之间文件不重叠才能并行，收口时全项目 sha256 指纹比对，归属外的任何改动直接阻断验收；二是状态机调度，exec_done 不等于 verified，主持 AI 必须读产物和测试退出码才算通过；三是可见性证据——通过 CDP 遍历 React fiber 树驱动桌面会话，要求『正确项目、选中会话、正文出现任务标记』三要素齐备才写证据文件，防止后台发成功了但人看不见的假执行。」

深挖点

  • CDP 桥：BFS 3 万节点找 React fiber 上的服务对象、动态 import chunk 拿 store——逆向但全离线可测试（vm 伪造 DOM）
  • 对称设计：调度器拒绝 engine===coordinator 的包，「主持方不能自己执行自己」
  • 模型策略：指定模型不可用明确失败不静默替换；零费率优先，Auto 不当免费
  • 零 npm 依赖 + 20 项离线测试 + PowerShell 5.1/7 双通道兼容

⑧ 面试题库 · AI 应用与工程Q&A

A1介绍一个你做过的 RAG 项目，完整链路是怎样的？

结合 spring-ai 仓库作答（16 个模块中最完整的是 AI-code-21）：

  • 离线入库：Tika/PDF/HTML Reader 读文档 → 拆分（对比过 TokenTextSplitter、语义拆分、递归拆分，观察过「换行符多拆的多」现象）→ qwen3.7-text-embedding 向量化（踩坑：批次上限 12，要分批）→ 写入 Milvus（踩坑：collection 名不能带 "-"），文档带 metadata 多标签。
  • 在线检索：用户问题先过 RewriteQueryTransformer 查询重写（自定义 prompt：扮演词汇清理专家，提取专业词汇提高向量检索精度）→ 向量检索（元数据过滤表达式、score 阈值）→ RetrievalRerankAdvisor 重排：向量库粗筛 topK=200 给 rerank 模型精排（similarityThreshold 0.4）→ 拼接上下文生成。
  • 兜底：allowEmptyContext(false)，检索为空时给模型明确提示而不是让它瞎编。

为什么两级检索：向量召回快但粗（topK=200 保证召回率），rerank 模型交叉编码精但贵（只对 200 条精排），这是「召回-精排」的经典权衡，和搜索推荐系统同构。

可能追问：三种拆分器怎么选？（结构化文档用递归保留层级、长文用 Token 控制窗口、语义拆分贵但边界的语义完整）；为什么需要查询重写？（口语化/多义词问题，重写后向量更接近知识库语料的分布）；Milvus 索引选型？（ai-project 里配过 ivf_flat + cosine，nlist/nprobe 取舍）。
A2大模型输出不稳定（格式不合规、编造内容）怎么办？

分层治理，每层都有项目实例：

  • 约束层：response_format: json_object 强制 JSON（GoTrip 解析攻略）；BeanOutputConverter 自动生成 JSON Schema 注入 prompt（spring-ai 结构化输出模块）；SupervisorAgent 的 instruction 直接写死「只输出 JSON 数组，完成输出 []」。
  • 校验层：GoTrip 飞哪儿 AI 建议要求返回的航班 id 必须来自候选集合，返回后用 availableIds 过滤——模型编造的 id 直接被丢弃；extractJson 兼容 ```json 围栏和裸 JSON 两种形态。
  • Prompt 约束：解析攻略时明确「严格保留原文顺序不重排」「不编造价格」「概要行并入当天最后一条 notes」。
  • 失败路径：解析失败降级到 builtinParseGuide 规则引擎，功能不中断。

经验总结：对 LLM 输出永远「约束 + 校验 + 兜底」三件套，不信任单点。

可能追问：json_object 模式的副作用？（会把回答包进 {"answer":...}，GoTrip 助手场景特意关掉）；JSON 解析失败重试策略？（有限重试 + 换更低温度 + 最终走规则引擎）。
A3AI 服务挂了/超时，你的应用会怎样？（降级与容错设计）

GoTrip 的设计原则是「任何情况不回落假数据，但功能永远可用」：

  • 功能级兜底：AI 解析攻略失败 → builtinParseGuide（6 组正则关键词分类 + 中文数字天数解析 + 路线型标题识别）；锦囊 AI 生成失败 → 20+ 城市手写内容库；助手失败 → 内置功能指南 FALLBACK_GUIDE。
  • 数据源降级：天气走高德 geocode→adcode→weatherInfo 主链路，失败降级 Open-Meteo（带 WMO code 映射表），全败返回诚实占位——每个数据带 source 标识（-2 高德源 / -1 占位），前端绝不把占位当真数据渲染。
  • 超时治理：微信 callContainer 15 秒硬超时 vs AI 任务 10–40 秒的矛盾 → 统一异步 job 化（submit 秒回 jobId + 轮询 + TTL 5 分钟 GC）；spring-ai 里工具调用用 CompletableFuture.orTimeout(3s) + exceptionally 兜底提示，超时设为外部 API 平均响应的 2–3 倍。
可能追问：兜底规则引擎的准确率？（不如大模型，但结构可用、用户可手动改——「可用性优先于完美」）；job 存内存行不行？（服务锁定 MaxNum=1 单实例可行，多实例要落 Redis）。
A4多轮对话的记忆怎么设计？

结合 spring-ai 的演进路径 + ai-project 的设计作答：

  • 存储演进：内存 → Redis（JedisChatMemoryRepository，窗口 10 条）→ MySQL（JDBC repo，窗口 5）→ 按 conversationId 多用户隔离。
  • 遗忘机制：消息数 ≥5 时触发专用摘要客户端（system prompt 工程化：保留用户核心目标/未解决问题/最新意图，第三人称，80–300 字，不加前缀），摘要后 clear 再回填摘要消息——手写了一个 SummarizingChatMemory。要点：摘要用便宜的小模型，主对话用大模型。
  • 隐私：自定义 BaseAdvisor，before 钩子里用独立脱敏客户端把姓名/手机号/身份证替换为占位符再进主链——双 ChatClient 架构，脱敏发生在消息进入主模型之前。
  • ai-project 的双层设计：Redis 短期记忆限 10 条上下文 + MySQL 长期记忆，会话结束可回溯。
可能追问：摘要丢失细节怎么办？（滑动窗口+摘要混合：最近 N 条原文 + 更早的摘要）；为什么脱敏放 Advisor 不放后处理？（进主链前脱敏，日志和上下文里都不留 PII）。
A5分享你的 Prompt 工程实践。
  • 结构化任务的 prompt 是「规格书」：GoTrip 的 PARSE_SYSTEM 细到枚举分天标记的四种写法（Day N / 第 N 天 / 「D5：10月5日：路线A-路线B」）、明确「餐：/行：/游：/住：」概要行的归属、禁止重排原文顺序、禁止编造价格——把解析器规格写进 prompt。

B1常见的 Agent 编排模式有哪些？

用 ai-image 的四种实现作答（同仓库可对比）：

  • 评估-优化循环（Evaluator-Optimizer）：writer 生成 → qualityEvaluator 评审 → 不 pass 就重写。我实现了两版：手写 while 循环版（直观、好调试）和 StateGraph 声明版（ReactAgent.asNode、KeyStrategy 状态管理、WORK_SUCCESS/WORK_FAIL 条件边、CompiledGraph.stream() 流式）——结论是简单循环手写够用，多分支/并行/需要重放时图编排优势明显。
  • 路由模式（Routing）：LlmRoutingAgent 靠每个子 Agent 的 description 让 LLM 选路，outputKey 隔离各自产物。
  • 监督者模式（Supervisor）：mainAgent 只负责把任务分解为 JSON 数组（如 ["create_agent","translator_agent"]），严禁自己动手——「规划与执行分离」。
  • 串行/并行流水线：SequentialAgent 用 {article} 占位符传递；ParallelAgent 三路扇出 + DefaultMergeStrategy 合并。
可能追问：循环怎么终止？（哨兵词【pass】/WORK_SUCCESS 结构化判定 + 最大轮数兜底）；状态在节点间怎么传？（KeyStrategy/ReplaceStrategy 决定覆盖还是合并）。
B2让多个 AI 工具协作，你会怎么设计？

直接讲 work-together 的方案（已上架 SkillHub）：

  • 角色分离：主持 AI 负责 Spec（目标/边界/逐条验收）→ Plan（任务包：id/prompt/files/acceptance/dependsOn）→ Verify；执行 AI 只做执行。调度器硬编码拒绝 engine 与 coordinator 相同的包。
  • 并发控制用文件归属：每个任务包声明拥有的文件，canStart 要求与在跑包的归属不重叠；realpath 链解析防 symlink 逃逸、Windows 大小写不敏感比较。
  • 状态机：queued→creating→dispatching→running→needs_user→exec_done→verified；依赖包必须前置 verified。
  • 验收：exec_done 只代表执行器说做完了；主持 AI 读 diff/测试退出码后显式 verify；收口时 boundaryChanges 做全项目指纹比对，归属外任何改动（包括主持 AI 自己迟写的文件）阻断。
  • 可见性：执行必须留下「正确项目+选中会话+正文任务标记」三要素证据，杜绝假执行。
可能追问：为什么不用 LangChain/AutoGen？（目标是驱动真实桌面工具干真实文件，跨工具编排是 CLI 框架做不到的；且零依赖可控）；needs_user 怎么处理？（自动生成介入卡，人工处理后 resume，planHash 校验拒绝中途改计划）。
B3怎么防止 Agent「假装干活」和幻觉？

work-together 的反幻觉体系：① 执行必须产生可见性证据文件（三要素校验）；② unknown 状态不自动重派（避免越错越多），显示失败用 open 修复现场；③ 不伪造会话——接口不可用就明确报告缺口而不是降级模拟；④ 指纹比对抓越界改动；⑤ SKILL.md 把「不得把自测称为主持方验收通过」写成行为契约。应用侧对应：GoTrip 的航班 id 候选集合过滤、来源标注（builtin/amap/ai）、占位数据不冒充真数据。

B4Function Calling 的工具怎么工程化管理？
  • 声明方式：@Tool/@ToolParam 注解式 vs MethodToolCallback 编程式（ReflectionUtils.findMethod + ToolDefinitions.builder 写 name/description）——description 是给模型看的接口文档，质量直接决定调用准确率。
  • 权限：Spring Security @EnableMethodSecurity 让工具方法上的权限注解生效——工具不是人人可调。
  • 稳定性：ConcurrentHashMap 结果缓存（选型理由写在注释里）；CompletableFuture.orTimeout(3s) + exceptionally 返回兜底提示，超时设为外部 API 平均响应 2–3 倍。
  • 实战案例：GoTrip 调飞猪 CLI——spawn 子进程 + 串行队列 + 450ms 节流 + 429 指数退避重试 3 次 + 双层缓存（原始 10min/结果 30min）+ inflight 去重，还踩过「缓存键漏 passengers」的坑。
B5如何评估一个 Agent 系统的质量？

用 party-games 的方法论迁移作答：核心思路是「把主观变成可度量」——① 结构化判定替代主观评估（哨兵词 pass/WORK_SUCCESS）；② 差分测试：与参考实现对跑比对序列，掼蛋修出 4 类缺陷、missing=0；③ 校准断言：AA 胜率 0.80–0.90 区间断言（实测 85.2% 与公认值吻合）；④ 行为指标：AI 出牌合法率、任务包 verified 率、执行区间重叠毫秒数作为并发证明。Agent 系统同理：任务成功率、越界率（指纹 diff）、人工介入率、重派率。

C1手写/设计一个五子棋 AI，你的方案？

wuziqi/ai.js（360 行）三层结构：

  • ① 单点棋型打分：候选点沿 4 方向取 9 格窗口，与模式串优先级匹配——连五 1,000 万 / 活四 50 万 / 冲四（含跳冲四 11011 等）3 万 / 活三 8 千 / 眠三 700 / 活二 500 / 眠二 100；组合加成：双四 +20 万、四三杀 +12 万、双活三 +3 万（计数器实现）。攻防一体：候选点 = 己方价值 + 对方同点价值 × 0.9。
  • ② 威胁强制应手：搜索每个节点先战术收窄——己方有成五点直接返回 win；对方 ≥2 处成五点返回 lose（提前判负剪枝）；恰 1 处返回 block，强制只搜拦截点。
  • ③ 迭代加深 α-β：深度 2→4 步进 2，超时丢弃当前层保留上一层完整结果；每层按分值重排根着法提高剪枝效率；分值 ≥ WIN_SCORE−100 提前终止；强制应手延伸——深度用尽但处于 block 态再搜 1 层，解决水平线效应。
  • 难度 = 参数化（easy 纯贪心+前 3 随机、medium 深度 2、hard 深度 4 + rootCap 16）。
可能追问：为什么活四 50 万 > 双冲四 2×3万+20万？（活四下一手必胜且无法同时防；分值表要保证「必胜态 > 强组合 > 单威胁」全序正确）；候选点怎么生成？（距已有棋子 2 格内空点，避免全盘遍历）。
C2德州扑克 AI 怎么做决策？

poker-ai.js：胜率 + 赔率 + 对手建模的规则引擎。

  • 蒙特卡洛胜率：每步模拟 300–2600 次（难度决定），部分洗牌优化——Fisher-Yates 只打乱前 need = 对手×2 + 剩余公共牌 张，其余不动（未被选中的牌保持原位不影响均匀性证明可以讲：只需保证被抽取部分随机）；对手牌力一旦超过己方立即 break 早退。
  • 决策阈值：翻前用「公平份额」fair = 1/(opps+1) 的倍数定可玩性（开局 1.85、3-bet 2.05 且限 3 次加注内）；翻后价值下注阈值 0.56 ± 位置/对手数/风格修正；面对下注所需胜率 = 底池赔率 + 0.02 + 加注惩罚。
  • 对手建模：本街加注次数 → 威胁系数；「跟注站」探测（弃牌率 <28%）→ 诈唬价值下降、价值下注可更薄。
  • 风格与失误层：每局随机 aggro/tight/bluff 人格；novice 有 22% 失误率（且失误跟注限半个筹码栈，不为失误送命）；大师 eff>0.90 非河牌 25% 概率慢打设陷阱。
可能追问：为什么不用博弈树/CFR？（非完美信息博弈状态空间爆炸，实时对局里蒙特卡洛+启发式是性价比解；CFR 离线训练成本高）；怎么验证？（20 万手牌力评估交叉验证 + AA 胜率校准 85.2%）。
C3现场写：德州扑克多人 all-in 的边池怎么分？

buildPots 分层切池算法：按玩家 totalBet 升序分层，每层池 = (本层 bet − 上层 bet) × 参与该层的玩家数，eligible 记录「投入 ≥ 本层金额且未弃牌」的玩家；差额归最后一池；平分时余码按座位顺序逐个分配。举例：A all-in 100、B all-in 300、C all-in 500 → 主池 100×3=300（A/B/C 竞争）；边池1 200×2=400（B/C）；边池2 200×1=200（C 独得回）。另有两个细节：refundUncalled 退还未被跟注部分；bettingComplete 以 acted + bet ≥ currentBet 判定街结束，加注重开行动权。

C4设计「转账最少」的 AA 结算算法。

贪心（shared/budget.ts）：算每人净额（垫付 − 应付），债权人降序、债务人降序（绝对值），头尾互相抵扣：min(债权, 债务) 成一笔转账，直到归零。最多 n−1 笔。两个工程细节：① 浮点容差 0.005；② 小程序版改为以分为单位的整数运算，取整余数记回垫付人保证总额守恒——两版对比可谈「金额永远不要用浮点累加」。补充亮点：行程体检算法（时间重叠、转场 <30 分钟且换地点、单日 ≥7 项预警）。

C5为什么 GPS 坐标显示在高德地图上会偏？怎么解决？

GCJ-02 火星坐标系问题（go-trip 的 gcj02.ts）：GPS 输出 WGS-84，高德瓦片用国测局 GCJ-02 加密坐标，直接叠加偏移 100–700 米。解决：实现标准转换算法——克拉索夫斯基椭球参数 + 正弦扰动计算偏移量，注意境内外判断（outOfChina 直接返回原坐标），转换是单向近似（GCJ→WGS 需迭代反向求解）。同类坑：POI 搜索返回的坐标已是 GCJ-02 就不能再转。

C6Zobrist 哈希置换表的原理和碰撞问题？

party-games 象棋 AI（xq-ai.js）：每个（棋子, 位置）组合预生成随机数，走子时增量 XOR 更新局面哈希（O(1)），置换表缓存「局面 → 搜索结果」，避免重复搜索。碰撞设计：双 32 位拼合而非单 64 位（JS 位运算 32 位截断问题），xorshift32 确定性种子保证可复现；TT 记录三态 flag（精确/下界/上界）配合 α-β 边界使用——只有 flag 匹配当前窗口才能直接返回，否则仅用于着法排序。着法排序：TT 置顶着法优先 + MVV-LVA（最贵 victim 配最便宜 attacker 优先）。

C7什么是静态搜索（quiescence）？为什么只延伸吃子？

解决水平线效应（horizon effect）：固定深度搜索在叶子处可能正好停在「刚被吃子还没回吃」的局面，评估严重失真。quiesce 在叶子处只延伸产生局面剧变的着法（吃子），直到局面「安静」再评估，限深 4 防止爆炸。五子棋里对应的是「强制应手延伸」——处于必须拦截的战术态时延伸搜索。两者本质相同：在评估前让局面到达稳定点。

D1HTTP 长轮询和 WebSocket 怎么选？你两个都实现过？

两个都实现了，场景不同：

  • 五子棋用长轮询（server.js 321 行零依赖）：GET /state?v=版本号 服务端挂起最长 25 秒（waiter Set，touch 时唤醒推送），客户端 AbortController 32 秒兜底 + 1.2 秒重试。选它：回合制低频更新、零依赖、穿透性好（不需要 Upgrade 头）、实现简单。

D2手写 WebSocket 协议（RFC6455）要注意什么？

dezhou-poker/server.js 494 行零依赖实现：① 握手：Sec-WebSocket-Key + 固定 GUID 做 SHA-1 → Base64 返回 Accept；② 帧解析：FIN/opcode、mask 掩码还原（客户端→服务端必须掩码）、126/127 扩展长度（127 用 BigUInt64 读 8 字节）；③ 分片重组：opcode 0 continuation 帧拼接到前一条消息；④ ping/pong 心跳、close 握手；⑤ 10MB 帧上限防内存攻击。掼蛋服务器还有独立一份实现 + WS ping 保活（死连接写失败触发 cleanup）。

D3为什么游戏逻辑要在服务端跑？直接信客户端不行吗？

防作弊 + 一致性：服务器权威架构。德州的引擎跑在服务端 vm.createContext 沙箱里（三份源码拼接注入，共享顶层 const 正则改写 var；DRIVER_SRC 把 UI 函数桩化为 hooks，真人行动由 humanTurnHook 返回 Promise 等 WS 消息 resolve）。底牌按座位脱敏：stateFor 只把底牌发给本人或已摊牌者——底牌在摊牌前不出服务器，抓包也看不到。断线 45 秒压到 5 秒自动代打；僵尸连接防护：action 消息校验 seat.ws === 当前连接，旧连接不能替已被认领的座位行动。

可能追问：为什么用 vm 沙箱不直接 require？（同一份引擎代码浏览器/服务端复用 + 隔离全局变量注入 hooks；vm 不是安全边界，防的是误操作不是恶意代码）。
D4讲一个你修过的并发 bug。

engine-host.js 的三个真实并发缺陷（都有回归断言）：

  • ① 超时回调引用了作用域外的 reject：引擎握手超时一旦真的发生就 uncaught ReferenceError 带走整个服务进程（引擎二进制卡死 = 全站下线）——改为走 st.starting.reject。
  • ② 旧进程迟到的 exit 事件误清新进程状态：重启后旧句柄的 exit 触发把新状态清掉——改为按进程身份把关（if (st.proc !== proc) return）。
  • ③ 并发第二个查询永久挂死：单飞队列里第一个查询 settle 后没人推进队列——改为 settle 内 pump + 按条目身份幂等结算。

共同教训：异步回调要携带身份，按「哪个实例/哪次请求」校验后再操作共享状态。

D5没有现成测试方案的黑盒系统，怎么保证正确性？

差分测试方法论（party-games）：写 Python harness 与参考引擎对跑数百局，逐帧比对手牌/出牌序列。战果：掼蛋修出 4 类缺陷（同花顺不进 AI 候选、A2233/AAA222 级牌回绕不认、三带二万能替换枚举不全、天王炸从不生成），斗地主对 rlcard 修出 3 类（首出缺四带二/飞机带单对/王炸、附件只出单一代表、未禁拆王炸作翅膀），最终 missing=0。加上 fuzz：25 万局随机局。核心思想：不验证「对不对」，验证「和参照物是否一致」——参照物可以是参考实现、公认常数（AA 胜率 85.2%）、或双实现交叉验证（20 万手牌力评估）。

D6讲一次你主动推翻自己架构的经历。

GoTrip 的架构反转（9/26，25 commits 的当天）：v1 是 Node 容器 + WebSocket 实时协作 + 自管数据库（经历了 SQLite→PG→MySQL 三方言）。迁移 CloudBase 后发现：数据模型权限是「仅创建者可读写」（_openid 行级隔离），跨用户共享行做不到；而实时协作 + 有状态容器是小程序审核和运维的最大风险面。决策：主动去掉实时协作——行程按账号独立、占位同伴用于分账、写操作落动态流，冲突面被「单人单库」直接消掉（乐观写 + 写后 reload 全量重拉）；Web 切 rdb 直连，容器瘦身为无状态代理（只守 AI/POI/机票密钥）。代价是「协作」退化，换来最短合规发布路径。教训：用产品语义换工程复杂度，发布比完美重要。

D7Serverless/容器平台的冷启动和探活有什么坑？

GoTrip 实战三连：① 云托管冷启动被 DB 初始化卡死，平台按 /health 状态码判活会反复重启容器 → 改为先 server.listen 再后台 initDb，/health 恒 200（可用性写在 body）；② 平台「写后立即 list」有可见性延迟 → 创建后用 createRows 返回的 idList，禁止写后立即 list；③ callContainer 必须带 X-WX-SERVICE 头，漏了全部容器 API 404。这些平台怪癖全部沉淀在 entities.ts 的注释里，并写进 7 条红线手册。

D8不依赖框架的 IPC/协议逆向要注意什么？

wb-buddy-checkin 的经验：① 安全边界优先：只走客户端 IPC 代发（endpoint+ticket 握手，鉴权头客户端附加），零凭据接触——客户端改登录态加密我也不失效；② 协议细节：HMAC-SHA256 四帧挑战应答、五段大端 uint32 长度前缀 transcript、双向验证（反向校验服务端 proof 用 compare_digest 防时序攻击）；③ 隐性约束要踩出来并记录：RPC 帧缺 mode 字段永远不返回、Windows 命名管道一读一写并发直接 EINVAL（解法：每次往返临时读线程 + join 超时 + broken 状态机）、HTTP 400 + body code 表达业务语义；④ 离线自检：7 项不联网自检验证协议实现（含 transcript 四路敏感性、NDJSON 粘包半包拆帧）。

⑫ 面试题库 · 系统设计题Q&A

E1设计一个智能客服系统（含知识库问答与转人工）。

直接用 ai-project 的设计作答：

  • 知识层：商户上传商品文档 → RAG 入库（Milvus ivf_flat + cosine，检索阈值 0.3、top5）；多租户用 tenant_id metadata 过滤。
  • 人设层：role 表 12 字段（沟通风格/解决问题思路/情绪智力/escalationCriteria 升级人工判定/结束语），prompt 组装时注入。
  • 会话层：WebSocket 双端点（商户/客户）+ 自定义编解码器 + 连接池；session 状态机 AI ⇄ HUMAN；消息 5 种身份 + 已读状态。
  • 记忆层：Redis 短期 10 条窗口 + MySQL 长期。
  • 兜底：检索为空明确告知未查到；低置信度/情绪识别触发转人工；流式组装逐帧推送。
E2设计一个多 Agent 任务编排系统。

work-together 的设计即答案：Spec/Plan/Verify 三段式主持 + 文件归属并发控制 + 状态机调度 + 依赖 DAG + 指纹验收 + 可见性证据。关键取舍：为什么文件归属而不是锁？（声明式、可在 plan 阶段静态验证冲突、支持并行窗口最大化）；为什么 sha256 全量指纹而不是事件监听？（不依赖执行器诚实上报，兜住一切旁路写入）。

E3设计一个短链系统 / 限流器。（系统设计笔记题）

system-design-notes 28 章是弹药库：短链（hash + base62 vs 预生成号段、301/302、缓存、冲突处理）；限流器（令牌桶 vs 漏桶 vs 滑动窗口计数、Redis + Lua 原子性、分布式限流、竞争条件）。结合项目落地经验：ai-image 用 Guava RateLimiter 做 2 QPS 的 Advisor 限流（tryAcquire 失败抛「系统繁忙」）；GoTrip 登录接口 IP+用户名 10 次/分限速 + Secure Cookie + 会话过期清理。可延伸谈一致性哈希（分布式缓存节点增减的最小迁移）、Snowflake（项目里见过分库分表场景的 ID 方案讨论）。

E4你的个人项目如果是团队协作/高并发场景，瓶颈会在哪？

展示对自身系统边界的清醒认识：GoTrip 当前「单人单库」架构天然回避了写冲突，若恢复多人协作：① 需要行级共享权限或自建授权层；② 写冲突要乐观锁（version 字段）或 CRDT；③ 活动排序的高频写适合队列合并。party-games 若高并发：长轮询的挂起连接是瓶颈（换 WS + 房间分片）；掼蛋/德州服务器单进程 vm 沙箱要按房间 worker 分发；任务队列（engine-host 单飞）要横向拆。核心：当前规模下我选了简单方案，并明确知道扩容的触发点和解法。
