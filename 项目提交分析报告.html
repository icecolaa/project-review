⑤ 出发吧 GoTrip —— 协作旅行规划平台Flagship

go-trip旗舰应用React 18 + TypeScript微信原生小程序CloudBaseNode 容器

225 次提交 · +105,855 / -29,964 行 · 9/6 – 9/30 · Web 约 8,700 行 + 小程序约 9,000 行 + 容器 2,400 行

项目定位

面向中国旅行者的协作旅行规划平台，仿 TREK 体验并做了国内深度适配。最终形态是 Web（React）+ 微信原生小程序 双端，数据全部落在腾讯云 CloudBase 数据模型（gt_* 表，_openid 行级隔离），自建 Node 容器只承担需要守密钥的 AI / POI / 机票代理。

功能全景

  • 每日行程编排：按天活动、拖拽排序、跨天移动、十种确认状态
  • 出发模式（Trip Mode）：全屏当天视图、逐站勾选、haversine 站间距、手绘 SVG 路线
  • 旅行地图：高德瓦片标准/卫星双图层、按天分色路线
  • 团队预算：AA 记账、分类统计、「转账最少」结算
  • 飞哪儿：机票低价探索（飞猪 AI 开放平台）+ 涨跌记忆
  • AI 助手：攻略文本解析成行程、一键生成行程、全站悬浮问答
  • 旅行锦囊：20+ 城市手写内容库 + AI 定制生成
  • 打包清单、旅行日志、攻略收藏、成员动态流、深色模式

AI 实现（本项目的核心特色）

  • 攻略 → 结构化行程（server/src/ai.ts）：OpenAI 兼容接口接入智谱 GLM/DeepSeek 等，response_format: json_object 强制结构化；System Prompt 精细到「识别 Day N / 第 N 天 / D5 分天标记」「严格保留原文顺序不重排」「不编造价格」。
  • 离线兜底：builtinParseGuide 用 6 组正则关键词分类 + 中文数字天数解析，AI 不可用时功能依然完整可用（source: 'builtin' 标注来源）——「任何情况不回落假数据」原则贯彻全站。
  • AI 结果落库（apply-guide.ts）：支持全量重建与「按天号精准替换」两种模式；写完自动批量地理编码回填坐标，失败不影响行程。
  • 异步 job 化：微信 callContainer 有 15s 硬超时，AI 生成/机票搜索需要 10–40s → 统一改为「提交秒回 jobId + 后台执行 + 轮询取结果」，任务 TTL 5 分钟 GC。
  • 防幻觉：飞哪儿 AI 建议要求返回的航班 id 必须来自候选集合（返回后过滤校验）；助手问答特意关闭 JSON 模式避免包裹。
  • 合规实战：个人主体小程序因「AI 深度合成类目」被微信驳回 → 用户可见文案全面「去 AI 化」、AI 对话页摘出注册流程，验收脚本断言 AI 页不可达。

架构演进（225 次提交的主线）

自托管 React+Node+SQLite → 迁微信云托管（MySQL 三方言 DDL）→ 架构反转：放弃自建 WebSocket 实时协作与有状态服务，切 CloudBase rdb 直连 + 无状态代理（为满足小程序合规与最短发布路径）→ Taro 中途弃用、改原生小程序 21 页重写 → 12 段分段自愈自动化验收框架（190 张截图、46/46 断言全绿）。

典型踩坑（均有提交实锤）

  • 云托管冷启动被 DB 卡死 → 先 server.listen 再后台初始化、/health 恒 200（平台按状态码判活会反复重启容器）
  • 平台「写后立即 list」可见性延迟 → 活动 day_id 全空；缓存键漏 passengers 导致 9 人缓存污染 2 人查询
  • PG 迁移语句接在 return 后成为死代码 → 生产缺表 500；js-sdk auth 失败不抛异常 → 「注册假成功」
  • 「全库导出接口在公网挂了 3 天」的安全事故复盘，沉淀为 7 条红线规则手册（CLAUDE.md）

⑦ work-together —— 多 AI 桌面协作工作流AI Engineering

work-togetherAI 工程Node ≥22 零依赖CDP 协议逆向SkillHub 上架 v1.2.0

13 次提交 · +1,689 / -146 行 · 10/15 – 10/18（4 天）· 28 个文件约 1,543 行

项目定位

一套多 AI 桌面协作工作流 Skill：主持方聊天 AI（Codex / ZCode / WorkBuddy 任一）负责 Spec → Plan → Verify，把执行指派给其他工具的桌面会话，在同一项目目录内按「文件归属」并行执行独立任务包——即「一个 AI 当架构师兼验收官，其他 AI 当外包程序员」的分工系统。

核心机制

  • 状态机调度（workflow.mjs，9 个子命令）：queued → creating → dispatching → running → needs_user → exec_done → verified；依赖包须前置 verified 才启动，并发受「并发上限 + 文件归属不重叠」双重约束。
  • 验收闭环：执行结束只算 exec_done，主持方读产物/diff/测试退出码后 verify 才算通过；收口时做全项目 sha256 指纹比对，归属清单之外的任何增改删都会阻断验收。
  • 对称设计：调度器直接拒绝 engine 与 coordinator 相同的任务包——「主持方不能自己执行自己」是硬约束。
  • 桌面桥逆向（cdp.mjs，最硬核部分）：经 Chrome DevTools Protocol 遍历 React fiber 树（BFS 3 万节点）定位任务服务，动态 import 会话 store 发消息；「可见性三要素证据」（正确项目 + 选中会话 + 正文出现任务包标记）齐备才写证据文件，防止「后台发成功了但人看不见」的假执行。
  • 模型策略：ZCode 固定指定模型不可用就明确失败（不静默替换）；WorkBuddy 按费率字段动态选零费率模型——「Auto/空费率不能当免费」是写死的防御。

亮点

  • 零 npm 依赖：原生 fetch / WebSocket / node:test；PowerShell 5.1 + 7 双通道兼容（记录了 JSON 数组包装、file URL query 等坑）。
  • 20 项测试全离线：用 vm.runInNewContext 伪造 DOM 跑真实可见性表达式；execFileSync 临时目录跑真子进程验证锁竞态。
  • 「证据链」文化：JSONL 快照、状态看板自动渲染、介入卡、可见性证据文件——反幻觉纪律（不伪造会话、不夸口、明确报告缺口）贯穿始终。

⑧ wb-buddy-checkin —— 签到自动化 SkillAI Engineering

wb-buddy-checkinAI 工程Python 标准库Windows 命名管道SkillHub 上架 v1.1.3

6 次提交 · +2,009 / -246 行 · 10/17 – 10/18（2 天）· 8 个文件约 1,763 行

项目定位

WorkBuddy 桌面端「每日积分」自动化 Skill：签到 → 连签进度 → 猫猫旅行一条命令闭环。走客户端本机 IPC 通道代发请求，全程零凭据接触——不解析加密登录态、不读进程内存、不落盘 token，鉴权头由客户端自己附加。

核心实现

  • 协议逆向（wbipc.py）：NDJSON + HMAC-SHA256 四帧挑战应答握手（五段大端 uint32 长度前缀 transcript），双向验证——不仅证明自己，还反向校验服务端 proof；隐藏约束「RPC 帧缺 mode 字段会永远不返回」被踩出并记录。
  • 命名管道并发限制：一个线程阻塞读 + 另一个线程写会 EINVAL → 每次往返临时起读线程并 join 超时，超时标记连接 broken 弃用。
  • 幂等设计：先查状态已签就不发领取请求；HTTP 400 + body code:10001 表达「今天已签」——协议层专门支持不抛错读响应体。
  • 给 Agent 的结果契约：--json 输出固定结构，Agent 只需判断 ok / 合法状态集 / anomalies 三条——把 LLM 的判断空间压缩到枚举匹配，并明写「不要读源码、不要展开推理」。
  • 离线自检：7 项不联网自检（base64url、transcript 长度前缀、证明对四路敏感性、NDJSON 粘包半包拆帧）。
  • 实测 bug 修复样本：无进行中旅行时接口把 buddy_id 归零导致误报 → 修为回查权威接口并回填名称稀有度。
